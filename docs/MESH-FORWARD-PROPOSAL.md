# Reviewed TCP service forwarding through a workspace

Status: **operator-approved scheme; ordinary builds deny new forwarding and generic transit authority pending remaining acceptance gates** (October 26, 2026). The requested feature is general TCP forwarding, including HTTP and other duplex TCP protocols, from an exact mesh node and named service to an authenticated local listener. It must reach destinations through several peers without requiring source–destination direct enrollment. The operator clarified that relays carry transport and do not choose destination services. Destination TCP access still requires its own exact grant.

## Approved concrete authority

1. The destination operator installs a **destination-local service grant** for one workspace generation, original source and final destination stable ID, membership generations, directory DER/SPKI, both complete endpoint certificate pins and SPKI, destination account, service name, **literal loopback IP and canonical TCP port**, grant revision, expiry, concurrent connections, per-direction bytes, shared byte rate, per-connection lifetime and local CPU/memory hold. Requests carry only the service name and exact grant revision. They cannot supply a host, port, DNS name, URL, Unix socket or redirect target. The destination dials the reviewed literal endpoint without HTTP redirect handling. Account, pins, membership, endpoint and grant are rechecked before dialing and during the stream. A missing/expired/revoked grant denies by default.

   The grant identifies a loopback address and port, not an application process. If another local process later takes that port, ARM cannot by itself prove it is the same service. Applications requiring process continuity need their own authentication/pinning or a future Manager-owned service provider binding.

2. In an `arm_forward_review` development build, a relay installs a generic reviewed workspace transport grant with a local CPU/memory hold, shared byte rate across all streams/directions under the exact grant and expiry. It carries opaque routed streams for the workspace without approving a class or named service. The final destination alone reviews service access. Legacy class-specific relay grants remain readable for replacement or revocation. Relays forward only to the next currently enrolled and pinned direct neighbor on the immutable simple path (at most eight IDs). They cannot select a requester address or receive the destination service grant. The route header currently exposes the service name for end-to-end binding; the relay does not use it for authorization.
3. The original source and destination use separate pinned mutual TLS 1.3 with the `arm.workspace.forward.v1` ALPN over the opaque routed carrier `/v1/mesh/forward/route` and subprotocol `arm.mesh.forward.route.v1`. The route binding includes service name, path, endpoint identities, class, route ID and expiry. A verified original certificate, not the prior hop, is the principal at final admission. A route replay or loop is refused. The carrier keeps eight global/two neighbor slots, 15-minute lifetime, 30-second idle cap, 64-KiB frames and 8-GiB directional cap; destination grants can only reduce these bounds. A 1-second final grant watcher and the carrier's current-membership watcher close live streams after a local revoke. A partition can delay remotely learned membership revocation within the existing 60-second workspace freshness bound.
4. The source listener defaults to an ephemeral `127.0.0.1` TCP port and requires a fresh 256-bit token saved to a new mode-0600 file. Raw clients send `ARM-FORWARD/1 TOKEN\n`; the native stdio adapter sends `ARM-FORWARD/2 TOKEN\n` and waits for a local `READY` acknowledgement after destination admission before sending application bytes. HTTP clients send `Proxy-Authorization: Bearer TOKEN`, which ARM removes before delivery. This is a **local access credential**, separate from mesh identity. The backend now owns the source listener through a Manager lease holding the exact port and CPU/memory until its accept loop and connections join. CLI start/status/list/stop/recover use this durable record; the token itself stays only in the new private file. A recovered listener without an original join remains charged as `needs_attention`. Explicit recovery requires the replacement backend's exclusive daemon lock, a reviewed exact key/reason and a successful exact port probe. It settles only the local port/resource charge; application bytes remain unknown. A recent connection can leave the strict port probe blocked by TIME_WAIT, so stop can truthfully return `needs_attention` until a later recovery.

   Starting the local listener proves its source membership and local resource admission, not that a destination grant is present. Every authenticated connection must still pass a fresh pinned route and destination grant check. The original listener also freezes the workspace generation, source/destination membership generations and complete local/original/destination/directory identities at start; a replacement identity or generation requires a new listener. This freeze is an in-process witness; a recovered listener is never adopted or restarted from its durable resource record.

   HTTP convenience mode accepts one ordinary origin-form request per connection. Transfer encodings, trailers, upgrades, CONNECT and `Expect` require authenticated raw TCP. Browser Fetch cannot set `Proxy-Authorization`, so this token scheme does not yet support ordinary browser navigation to the forwarded service. `arm mesh forward stream` supplies a token-file-backed stdin/stdout client for programs that can use pipes. Unmodified arbitrary TCP clients cannot emit the raw token preface, and that stdio command does not make a tokenless loopback port safe from other local OS users. A browser credential handoff and a transparent general-client interface that keep secrets out of URLs and preserve cross-user isolation remain product gates.

5. A forwarded TCP stream can have application effects before a route loss. Its result is **unknown**; the source does not retry it or reinterpret a relay acknowledgement as completion. The current TCP class has no application-level receipt. Operators must use the application's own idempotency/status operation for recovery. SSH and sync continue to use their typed original keys, endpoint grants, roots, resource admission and independent receipts. **`ClassSync` remains refused** by the routed SSH final handler until the fixed worker and public sync dispatch are wired; a TCP service grant never authorizes sync roots, arbitrary rsync commands or receipt substitution.

### Browser access candidates for separate review

1. **Dashboard-launched, modern-browser Basic session.** A current authenticated dashboard session would prepare a one-use, short-lived launch intent bound to the exact source listener key and browser session. The dashboard would submit that intent in a form body to a reserved path on the source listener, with an exact dashboard `Origin`. The listener would require the matching intent, exact literal-loopback `Host`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`, and `Sec-Fetch-Site: same-site` for that exact dashboard-to-listener hop before issuing a Basic challenge. After the operator enters the private local bearer, it would consume the intent and navigate to the service. Subsequent service requests would require the cached Basic bearer and `Sec-Fetch-Site: same-origin`; different-port `same-site`, `cross-site`, absent/invalid metadata and direct `none` navigations would be refused. `Origin` when present must match the exact listener origin. This deliberately makes address-bar entry, external links and browsers without the required Fetch Metadata unsupported. The listener would strip Basic `Authorization` before delivery, so destinations needing their own `Authorization` are unsupported in this mode. It must also refuse or safely handle destination `WWW-Authenticate`, redirects, cookies, service workers, WebSocket upgrades and current HTTP parser limits before implementation. A one-use launch intent and this strict [Fetch Metadata contract](https://w3c.github.io/webappsec-fetch-metadata/) need rendered cross-origin, same-site/different-port, redirect-chain, request-smuggling and browser-profile tests; the standard notes that `Sec-Fetch-Site: none` can persist through redirects, so a bare `none` navigation is insufficient. No launch intent, Basic challenge or browser credential cache is enabled today.
2. **Dedicated browser/client-certificate integration.** A browser profile could authenticate to a separate loopback TLS listener without consuming the forwarded service's `Authorization` header. This requires explicit certificate/trust installation and removal, per-profile isolation, exact Host/origin policy, session revocation and CSRF protection because browsers can send client certificates automatically. Installation and browser trust changes require their own reviewed operator decision. Nothing installs trust or changes a browser profile today.

Neither candidate changes destination grants or relay behavior. Both must prove that another local OS user and an unrelated website cannot obtain forwarding authority; no bearer may appear in a URL or downstream headers/trailers. Ordinary browser service access remains required.

## Current code and acceptance boundary

`internal/meshforward` validates exact grants and provides a bounded, paced, duplex destination proxy. The local policy ledger records destination TCP grants and a generic workspace transport resource envelope under compare-and-swap operator review. The server has a separate forward route handler and destination Manager hold; the CLI has `arm mesh forward grant|revoke|show|start|status|list|stop|recover|stream` and `arm mesh ssh-relay grant-relay` for generic transport. The browser dashboard has local source start/status/list/stop/recover controls; it displays a fresh token for private saving and sends only the digest. It does not offer destination grant edits or transparent service navigation. An actual three-daemon server test crosses B→A→C, posts HTTP on two separate connections, exchanges raw duplex TCP through another named service, denies an ungranted service, checks a four-byte ceiling, closes a live stream after generic relay transport withdrawal with joined charge settlement, restores transit and separately closes a live stream after destination-grant revocation. A compiled macOS public CLI fixture separately passes B→A→C HTTP and raw duplex TCP, token-file stdio access with admission acknowledgment, local token denial, per-service destination revocation, source lifecycle and exact resource-only recovery after TCP TIME_WAIT. It does not yet prove a physical cross-host firewall barrier, network partition/alternate-path breadth, public Linux end-to-end operation, rendered web/Charm parity, or formal refinement. The operator approved this exact scheme on October 26, 2026. Production rollout remains contingent on the outstanding acceptance gates.

## Release fence and remaining acceptance

Ordinary builds refuse TCP source start, forwarding-route admission and generic relay transport authority. The existing class-specific SSH/sync relay grant path remains available. `arm_forward_review` is a development-only build tag for isolated candidate testing, not a production enabling command or operator approval. Grant inspection, revocation, historical reads and exact resource recovery remain available. Generic relay pacing is shared across all streams and both directions under an exact grant, including SSH and TCP handlers; at most 256 unexpired grant revisions retain pacing state, and a full table denies new revisions.

See [the independent integration review](MESH-FORWARD-REVIEW.md) for findings, evidence and remaining gates.

## Operator decision

The operator clarified: relays only carry transport; they do not decide which TCP service to accept. Destination grants make that decision. Generic relay transport holds remain bounded and reviewed for resource use. The destination endpoint remains a literal loopback TCP address, and the source listener requires local token authentication.


## October 26 operator approval

The operator explicitly approved the concrete security scheme in this document.
That approval preserves the endpoint address/port identity limitation and does
not approve either browser access candidate, trust/profile installation, Basic
fallback or relaxation of accounting/identity checks. The ordinary-build fence
remains until implementation and acceptance gates are closed; original EOF
uncertainty and platform/formal/interface gaps remain recorded.

# Leased file synchronization over ARM SSH

Draft implementation proposal, October 25. The operator replaced the mounted-share direction with fast file synchronization: push, pull and **both directions**, with independently configurable endpoint behavior. Mounts, S/F snapshot services, mount adapters and their delivery requirements are removed from the future product scope. This document proposes the replacement; it does not claim an implemented sync command.

## Operator contract

Use the existing authenticated, destination-leased ARM SSH path. A sync runs as the selected destination account, with that account's ordinary filesystem permissions. SSH execution is not a sandbox; neither encryption nor ARM accounting confines an already authorized arbitrary remote command. The sync implementation itself limits its file operations to the reviewed roots. No new daemon port, OS service, mount, privileged setup, key distribution or system rsync installation is required.

Proposed commands, with endpoint roots always naming directory **contents**, avoiding implicit trailing-slash semantics:

```sh
arm sync push HOST --local ./project --remote /work/project --mode additive --reason "Upload source" --key KEY
arm sync pull HOST --local ./results --remote /work/results --mode full --reason "Retrieve results" --key KEY
arm sync both HOST --local ./project --remote /work/project --local-mode additive --remote-mode full --reason "Reconcile work" --key KEY
arm sync ... --dry-run
arm sync lookup HOST --key KEY
```

`additive` is the default receive policy. It creates new entries and updates changed entries; it preserves entries existing only at that receiving endpoint. It does **not** mean “never overwrite.” `full` also applies the reviewed removal rules below. In one-way push/pull, `--mode full` mirrors the selected source into the selected receiver, including removal of receiver-only entries shown in the preview. The sender's files remain untouched. In `both`, `--local-mode` and `--remote-mode` govern receipt of changes at their respective endpoints; `--mode` is rejected as ambiguous.

Preview identifies both host/account/root identities, direction, endpoint policies, baseline generation, resource promises, new files, overwrites, metadata changes, removals and conflicts. Mutation uses the existing concrete review/confirmation convention (`--yes` for noninteractive callers), bound to that exact plan. No additional permission ceremony is needed for the already requested full mode. A changed plan, root identity, grant or baseline requires a fresh review. There is no implicit move or delete-source option.

## Bidirectional reconciliation

The durable baseline belongs to the exact ordered endpoint pair: host/enrollment/account, named root plus native directory identity, selection/filter and metadata policy. It records each endpoint's last confirmed per-path state and deletion tombstones, not just one “identical tree” hash. Independent additive policies can intentionally leave different trees.

| Change since the last jointly confirmed baseline | Proposed result |
| --- | --- |
| First sync: path only on one side | Copy to the other; never infer deletion without a baseline. |
| First sync: equal path and content/type/selected metadata | Record agreement. |
| First sync: unequal entries at the same path | Conflict; no time-based winner. |
| One side edited, other unchanged | Copy the edited version to the other endpoint. |
| Both edited identically | Record agreement. |
| Both edited differently, or file/directory/symlink type collision | Conflict. |
| One deleted, other unchanged | Delete the other only if its receive policy is full; otherwise retain it explicitly. |
| One deleted, other edited | Conflict, including when full is enabled. |
| Both deleted | Record the tombstone. |
| Missing/partial baseline, replaced root, or uncertain prior round | No inferred deletion and no new baseline; inspect/reconcile original work first. |

A retained additive copy must not resurrect an unchanged deleted source on the next run: the baseline records that asymmetric outcome and the origin tombstone. A later actual edit of the retained copy is a new change, handled explicitly against that record. Tombstones cannot expire merely by age while their peer may still be offline. Baseline retention/compaction requires an acknowledged generation fence.

The default refuses mutation when unresolved conflicts remain. An explicit reviewed resolution file maps exact conflict paths and observed old hashes to `keep-local`, `keep-remote`, `keep-both` with exact new names, or an explicit deletion. Resolution is part of the immutable request/plan hash. A rename is initially represented as content reuse plus the corresponding create/removal decisions, not guessed from timestamps.

## Owned Go implementation and transport

Recommendation: implement a bounded ARM-owned Go planner/reconciler and rolling-block delta engine. Use standard rsync/openrsync as independent compatibility and performance oracles. Do not make the maintained upstream C executable a runtime dependency, and do not embed an unaudited third-party receiver merely because it is written in Go. The strongest reusable candidate is `gokrazy/rsync`; a narrowly patched, tested reuse may replace the delta implementation if its bounds, cancellation and filesystem behavior meet the same contract. Bidirectional baseline/conflict management remains ARM-owned either way.

The transfer engine uses receiver-generated block signatures, a rolling weak checksum and a strong checksum to find reusable ranges, streams literal/range tokens, verifies reconstructed length and a complete strong content hash, and publishes each file through a same-directory temporary file and rename. First transfer streams whole files efficiently. Use buffered sequential I/O and bounded parallel files under the CPU/memory/disk/FD promises; do not reopen an unlimited number of files or allocate a signature table directly from a peer count. Spill large manifests/signature partitions to charged temporary storage. Avoid hashing unchanged bytes twice without a correctness reason. File size/mtime quick checks alone cannot prove an approved overwrite or successful content equality.

Separate the ARM reconciliation/control protocol from its delta payload. Existing `ssh_account`, reviewed host-key pin/enrollment, `ssh_admit`, one-use stream and destination `AcquireSSH`/`SSHExecute` own execution. Refactor the existing CLI SSH stream plumbing into a reusable typed client, preserving source intent-before-execution, no PTY, fixed command digest, final revalidation and exact lookup. Invoke a fixed self-contained `arm sync-worker` entry from the already verified runtime executable, not PATH-selected rsync, a shell-expanded user path or an arbitrary option string. A small versioned stdin control message carries the exact plan/root/direction; binary payload uses the same encrypted channel. Do not enable generic SFTP forwarding or a public rsync daemon as a shortcut.

For pull, the remote endpoint is the reader and local receiver is an owned local worker with its own CPU/memory/disk obligations; for push the roles reverse. For both, each endpoint has read and write duties. Validate current existing SSH authority, effective account and root permissions at both ends. There is no new mount/share grant. Expose accurate source and destination resource/accounting limits; SSH execution TTL alone does not reserve local staging disk. If a selected path belongs to managed ARM storage, retain the existing ordinary storage lease/attachment protection through actual worker settlement.

## Mesh relay

Both ordinary SSH sessions and sync streams must also work over reviewed mesh graph paths when endpoints lack a direct connection. Carry the end-to-end authenticated encrypted SSH/ARM stream through bounded relays, preserving original source and destination identities. Each destination still checks its own current execution/file authority, resource budgets, account and enrollment; relays do not lend permissions or inspect plaintext. Reuse the existing graph identity/path machinery, retaining replay, loop, length, byte, stream-count and lifetime bounds. This is a narrowly typed SSH/sync relay, not arbitrary TCP forwarding. Any new introducer/transitive trust or relay-admission permission requires a concrete security review before it is enabled; existing message-only workspace membership alone must not silently grant shell/file access. Native acceptance must include a three-node no-direct-path SSH invocation and push/pull/both sync, relay loss/revocation and unknown-outcome recovery.

## Filesystem, durability and cancellation boundaries

Open each selected root with no-follow checks, retain the original directory/volume identity and recheck its current named binding before mutations. Reject same-tree overlap and dangerous selected roots rather than interpret them as a whole-host mirror. All relative paths are length/depth/byte bounded, unambiguous and traversal-resistant. Refuse absolute/`..` entries, duplicate normalized names and case/Unicode collisions that cannot be represented on the receiving filesystem. A symlink is copied as a link when supported; it is never a traversal authority. New descendants remain under the held root; replacements of the root or an ancestor invalidate the operation.

Ordinary permissions, executable bits and mtimes have explicit policies. Ownership, ACLs, xattrs, hardlink topology, sparse allocation and platform-specific metadata need capability negotiation and native tests; unsupported requested fidelity is an error, not a silent success. Devices, sockets and FIFOs do not become remotely created special files by default. Hardlinked receiver files are replaced by a new inode instead of modifying other links in place.

Before overwrite or removal, recheck the exact named receiver entry and its reviewed old content/type/metadata state. An **observed** concurrent local edit is a conflict, not permission to discard it. A hash check followed by ordinary rename/unlink is not an atomic conditional update against external writers. The receiver therefore needs same-filesystem native capture: exclusive publication for new names, atomic replacement preserving the displaced entry, and rename-to-owned-quarantine for removals. Validate the actually captured old entry before discarding any preimage. Native primitive availability and replacement/root races need real Darwin/Linux tests; there is no silent fallback to blind truncate/unlink. Keep every uncertain displaced variant in charged recovery storage. A late conflict can have partial visible effects and must report them; do not promise a transaction over live arbitrary user writers. Source/current permission checks are observations at the transfer/mutation cuts, not continuous source stability.

Stage and verify content, retain the original owner through close/sync/rename and journal the observed outcome. Full removals operate only on exact reviewed entries beneath the receiver root; no recursive “delete everything absent from the wire list.” New/unreadable/unexpected entries stop deletion. Stage all required received data before the deletion phase, and expose partial outcomes honestly. Baselines and operation journals live outside selected synchronized contents. Cross-host and multi-file publication is not atomic.

Both endpoints persist an operation key/plan digest before effects, record per-file progress and publish a confirmed baseline only after exact completion receipts agree. A crash can leave committed files on one side and pending work on the other. Lost SSH/Commit acknowledgments mean unknown, never success or rollback. Explicit original-key lookup inspects receipts; it must not re-run the transfer. No automatic new-key escape. An explicitly reviewed continuation is bound to the same operation and rechecks every remaining precondition; it cannot repeat an uncertain overwrite/removal blindly.

Cancel/TTL expiry/Stop closes admission and requests cooperative cancellation, then waits for the actual original transport/copy workers and native handles. Charge obligations until real join and staging cleanup observation; a context timeout alone is not reclamation. Keep partial files isolated and attributable. Recovery discovers retained work and reports it; it does not restart a delta transfer or advance the baseline automatically. Audit includes endpoint identity, policies, plan/baseline hashes, actions/counts/bytes, conflicts and outcomes, excluding keys, tokens and file contents.

Implementation should use focused normal diffs: remove dead mount/share surfaces with compiling guarded recovery; implement owned one-way delta engine and durable key receipts; implement the full shared-baseline bidirectional reconciler and per-end policies; then CLI/web/Charm and native/formal/performance acceptance. One-way completion is an intermediate milestone, not completion of the requested scope.

## Focused acceptance plan

* Unit/fuzz real decoder bounds before allocation, length/count arithmetic, signature collisions, corrupt tokens/hash/EOF, duplicate paths, path normalization and unsupported type/metadata. Real temp-directory controls cover symlink/ancestor/root replacement, hardlinks, denied permissions, disk-full/close/sync errors and no modification outside the selected root.
* Table tests cover first union, all four additive/full endpoint combinations, edit/edit, edit/delete, equal edits, local deletion with additive retention without resurrection, tombstone acknowledgment, changed policy, lost/reset baseline, stale plan and explicit conflict resolutions. Assert exact file bytes and both endpoint receipts after every result, not just command exit.
* Owned process/transport tests cover denial/revocation/enrollment and account changes, pre-admission cancel, mid-literal and mid-range cancel, crash before/after file rename/removal and before/after each baseline Commit, lost replies and read-only same-key lookup. Preserve charged/unknown duties; prove no replay or blind restart.
* Run actual Darwin/Linux ARM64 and AMD64 paths (native execution where claimed), push/pull/both over ARM's existing SSH, never loopback-only acceptance. Use actual installed system rsync/openrsync versions as recorded content/delta and performance oracles on matched inputs. An ARM-owned delta protocol need not implement the rsync wire format; if upstream protocol27 code is reused, separately test its claimed interoperable subset and refuse unsupported options explicitly. Standard rsync has no bidirectional conflict/baseline semantics to serve as that oracle.
* Measure fresh bulk copy, unchanged tree, small edits/insertions in large files, many small files and bidirectional conflicts on the actual native↔Linux link. Compare bytes on wire, elapsed throughput, CPU and peak memory/staging disk against system rsync on identical data/options/encryption. Retain the agreed 85–90% same-pair encrypted streaming throughput target for applicable bulk transfers; do not claim it from cross-compilation or a changed-file speedup ratio.

No new runtime, dependency installation, source deletion or sync mutation was performed for this proposal.

## Primary-source implementation research

Review pin: [`gokrazy/rsync` v0.3.8, commit `7a9e59b40898516def209eb944c49f2ba42d4007`](https://github.com/gokrazy/rsync/releases/tag/v0.3.8). The public tree has 126 files, including 20 Go test files. This is source inspection, not an execution of upstream tests.

* **Strongest Go candidate:** full sending/receiving client/server, embedding and rolling delta. The project documents a smaller maturity/user base than original rsync and best-effort maintenance. Its protocol ceiling is27. These are reasons to audit and test a bounded subset, not evidence it is unusable. [README](https://github.com/gokrazy/rsync/blob/7a9e59b40898516def209eb944c49f2ba42d4007/README.md), [protocol constant](https://github.com/gokrazy/rsync/blob/7a9e59b40898516def209eb944c49f2ba42d4007/consts.go).
* **Meaningful existing tests:** CI lists macOS/Linux/Windows; Linux also tests Debian/Fedora rsync environments. Its macOS test command uses `sudo`, so it does not establish ARM's required unprivileged behavior. Interoperability tests exercise both directions, nested paths, exclusions and remote commands; existing tests are a useful starting point, not ARM ownership/cancellation proof. [CI](https://github.com/gokrazy/rsync/blob/7a9e59b40898516def209eb944c49f2ba42d4007/.github/workflows/main.yml), [interop tests](https://github.com/gokrazy/rsync/blob/7a9e59b40898516def209eb944c49f2ba42d4007/integration/interop/interop_test.go).
* **Concrete bounds work before embedding:** `SumHead.ReadFrom` rejects negative checksum counts but imposes no positive count maximum; sender `receiveSums` allocates a slice using that count. Receiver block lengths can reach512MiB. ARM must enforce admitted signature/metadata/literal bounds before allocation, plus cancellation, exact close/join and selected-root mutation preconditions. These are integration gaps, not a claimed reproduced exploit. [header reader](https://github.com/gokrazy/rsync/blob/7a9e59b40898516def209eb944c49f2ba42d4007/types.go), [sender](https://github.com/gokrazy/rsync/blob/7a9e59b40898516def209eb944c49f2ba42d4007/internal/sender/sender.go), [receiver](https://github.com/gokrazy/rsync/blob/7a9e59b40898516def209eb944c49f2ba42d4007/internal/receiver/receiver.go).
* **Embedding boundary:** `rsynccmd.Cmd` accepts streams, context and a dial callback; `Run` enters its command implementation. This can reuse an encrypted transport, but does not supply ARM's reviewed roots, per-path CAS or two-ended baseline. [API](https://github.com/gokrazy/rsync/blob/7a9e59b40898516def209eb944c49f2ba42d4007/rsynccmd/rsynccmd.go).
* **Other Go candidates:** `kaiakz/rsync-os` explicitly lacks rolling block exchange and currently supports only receiver/client; `jbreiding/rsync-go` supplies an algorithm, not a complete rsync wire/SSH endpoint or reconciler. Neither is a strong drop-in for this scope. [rsync-os](https://github.com/kaiakz/rsync-os), [rsync-go](https://github.com/jbreiding/rsync-go).
* **System compatibility:** the original manual specifies remote-shell push/pull, quick-check behavior, delta transfer and ordinary remote account access. Full rsync option/metadata parity is much broader than a protocol-compatible content engine. Keep the selected supported surface explicit and test actual platform binaries; do not infer that arbitrary current `-a`, ACL/xattr, compression or protocol30+ flags work. [upstream manual](https://github.com/RsyncProject/rsync/blob/master/rsync.1.md).

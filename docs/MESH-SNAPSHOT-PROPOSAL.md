# Optional snapshot generations and bounded read delivery

**Proposed, disabled, not approved or implemented.** Strict live-path shares remain available with their current native checks. This proposal adds a distinct read-only mode; it does not complete public mounts, writable/build coherence, the macOS adapter, or the performance target.

## The behavior being approved

Initial S copies explicitly selected regular files into a **new private managed allocation on the same origin host/account/provider**. Cross-host consumers are separate staged admissions; cross-host snapshot creation/replication is not enabled by this initial approval. An agent can request a **snapshot generation** of explicitly selected regular files in its ARM-managed storage. ARM reserves a separate storage lease, makes an independent private copy (or supported copy-on-write clone), verifies its complete contents, then publishes that exact generation. The operator reviews source identity/revision, selected files, recipient hosts/accounts, reason, resource budgets, retention and snapshot semantics.

Until publication commits, ARM retains the original source dependency and rechecks its current lease/grant/native identity and access. Source expiry, revoke or a failed original-path/access check before that cut prevents publication and begins exact staged-copy cancellation/settlement; holding a pin never renews entitlement. A verified private copy alone grants no publication or consumer permission. Once prepared, the exact publication review has at most **five minutes**, reduced by all earlier source/destination/grant deadlines; polling, default-no, lost replies and restarts do not restart that clock.

After publication, editing, renaming, deleting or changing the ACL of the **original** source does not change or recall this generation. Recall uses ARM revoke/release/expiry. A new snapshot is a new reviewed generation; it never silently updates an existing mount. Applications see read-only files, not a live build workspace. A clone is an economical way to copy; it is not an immutable or free object.

The snapshot itself remains an ARM-owned, charged storage object. It is not adopted from an export pathname. Its hashes identify content; host/account/grant/lease checks authorize access. Read-only mode bits are defense in depth, not a seal against arbitrary same-user programs. Root and arbitrary same-user code are outside ARM's strong isolation boundary. On every platform, verified content and exact retained generation ownership remain mandatory; native sealing is an optional tested strengthening.

## Two separate decisions

| Choice | Proposed behavior | Security consequence |
| --- | --- | --- |
| **S: snapshot mode** | Original-source native path/ACL checks occur during creation. Published reads use exact copied-generation descriptors, chunk verification, fresh ARM authority checks and ordinary local lease checks. No data is served under the original file's later ACL. | Explicitly decouples source changes from a published generation. It preserves immediate origin refusal on current authorization changes; content already sent cannot be recalled. |
| **F: bounded delivery delegation, only with S** | Each credit covers exactly one canonical manifest chunk: aligned one MiB, or the shorter final chunk. At most eight simultaneous slots/eight MiB per consumer cover pending requests, partial fetches, verified data and pinned/ending work; data remains charged until actual settlement. Each credit has at most 250 ms of validated suspend-aware lifetime anchored before its request is queued/sent. Unaligned application reads use up to two exact chunk credits. The adapter verifies each whole chunk and checks fresh local authority plus every required unexpired origin credit before each data-bearing FUSE read response. | It replaces a fresh origin round trip for every 32 KiB delivery with an explicit short delegation. A remote revoke/partition can leave an unexpired delivery tail of up to the approved credit lifetime. This is not immediate fresh remote revocation checking. Prefetched bytes have already been disclosed to the recipient host. |

These are simultaneous ownership/authority limits, **not** an eight-MiB-per-250-ms rate limit. A spent or expired credit does not free still-owned buffers, fetches or work. Fresh credits require fresh origin admission and a new request anchor, with all eight-slot/eight-MiB and aggregate limits still enforced. Metadata/open/list operations retain S's current origin checks; data possession is never permission.

Recommendation: approve **S only** first if the source-decoupling behavior is wanted. F is a separate optional semantic approval; implement it only after the exact chunk/control/handoff contract and its clock, recall, replay, accounting and real ordinary-application gates pass. Either can remain disabled. Immediate recall policy excludes F. Both ends must explicitly allow the selected mode and limits; an existing connection or strict share grant does not opt anyone in.

## Why this may help, and what is unknown

The accepted comparison measured ordinary mounted reads at approximately 44 MiB/s, against 222–237 MiB/s with explicit one MiB application reads. Ordinary reads produced about 4,100 requests for 128 MiB; explicit reads produced 129. The existing profiles also show considerable native verification/open work. These observations motivate a separate generation object and bounded user-space range fetches; they do not prove a cause or predict the result.

S can remove repeated original-directory opens without pretending that a held original FD proves current original ACL permission. However, one synchronous remote authorization/read for each ordinary request can still be slow. SFTP supports multiple outstanding requests, but it cannot pipeline application requests that do not yet exist. F supplies a reviewed chunk-credit mechanism so a user-space adapter can fetch verified larger ranges and answer ordinary small reads locally. It does not change the application buffer, enable kernel page caching, or silently weaken strict mode. Safe pipelining uses existing bounded transport credits and dedicated revocation capacity, not unlimited requests.

The project's target remains approximately **85–90% of the paired raw pinned-TLS encrypted network-stream baseline between the same hosts**, for appropriate large sequential workloads. The current raw-TLS reference is about 1,350 MiB/s (1.32 GiB/s); the separately verified-file stream (about 620 MiB/s, including current filesystem checks) is a diagnostic, not a lower substitute denominator. Neither the ordinary-read results nor the explicit one-MiB application-read results replace the raw-network baseline. A different target would require an explicit operator decision. The latest 36 samples do not establish feasibility, improvement, regression or statistical significance. Both cold and warm reads, metadata, mixed/random access and real workload behavior still need measurement. Full writable/build semantics remain separate required work.

## Authority, expiry and recall

Retain pinned TLS 1.3 mutual authentication and destination-owned admission. No new transitive mesh access, arbitrary forwarding, system daemon, privileged mount helper or account is introduced. Snapshot publication, per-generation reading, consumer mounting and optional F are separate directional decisions. Every admission binds both host IDs/accounts, enrollment/certificate/grant revision, exact generation/manifest/mode, local and remote lease IDs, recipient session/boot, operation key, reason and budgets. Equal numeric UIDs across hosts are not identity.

Creation and publication are separate denied-by-default decisions: neither an existing strict share grant nor a successful copy permits a new retained publication. In S, every origin operation checks current origin authority before returning bytes; the receiving adapter checks its local consumer authority before each response. In F, current origin authority is checked when the exact chunk credit and data are issued, and each later data-bearing adapter response must present unexpired, unspent credits for every covered chunk, bound to that same generation/session. Overlapping/repeated application reads spend their full response bytes again; a response spanning two chunks atomically spends the intersections from both credits. Origin fragment disclosure and local delivery are separate counters. Already handed-off bytes never regain allowance merely because a response or acknowledgement was lost. Credit lifetime is never renewal. Local release/revoke/expiry denies new local responses immediately upon its local authority transition. Received remote revoke closes the credit epoch and discards cached delivery permission. A partition prevents new credits; old ones can be used only within the explicit approved tail. Immediate remote recall cannot be promised across a partition.

Use a validated clock that includes suspend; check its deadline before copying into each response, not only through a timer callback. Credits never survive reboot, daemon restart, changed boot/clock domain or uncertain clock quality. There is no serialized cross-host monotonic timestamp. Record each request's elapsed start and nonce before transport admission/queueing, so a delayed reply consumes the request's lifetime rather than starting a new one on arrival. Every fragment/replay for that nonce retains the original nonincreasing deadline. Wall-clock rollback cannot extend entitlement. Detailed clock and replay obligations are in [technical contract](MESH-SNAPSHOT-TECHNICAL.md).

Already copied bytes, recipient-host buffers, application memory and authorized file copies cannot be clawed back. Prefetch is a real data disclosure and is charged when sent, even if the application never uses it. The recipient cannot claim an unused cache as proof of nondisclosure or remote reclamation.

## Costs and failure behavior

Initial scope: at most 64 explicit regular files and 16 GiB logical content, matching the existing export selection bounds; recursive directory publication is a later capability, not silently inferred. Source and destination hold separate full-copy logical promises while both exist; measured allocated blocks, shared-pool free space and unknown reclaimable bytes are separate quantities, never summed as independent physical usage. Copy-on-write extents, snapshots and APFS shared pools are never summed as independent space, nor does cloning prove zero cost or guaranteed reclaim.

Admission records explicit CPU/copy concurrency, disk ceiling, manifest, FD, memory, cache and retention limits **before** work. There is no free unbounded snapshot or automatic capacity expansion. The source remains pinned through the final publication decision, or through cancellation of the exact unpublished intent, and until its original copy/native work really joins. An abandoned/default-no prepared review expires within its at-most-five-minute budget; expiry fences publication and starts ordinary settlement without making unknown work free. Destination staged data remains separately charged until its own verified cleanup. The new storage lease continues after original source cleanup. The generation remains charged until its consumers, data/control streams, prefetch tasks, pinned buffers, mounts, native descriptors and cleanup are positively settled. Timeout, lost acknowledgement, missing path, or an unlink while a descriptor is open does not settle that duty.

On restart, exact recorded keys are lookup/reconcile only; no blind recopy or second publication. Unknown workers/streams/mounts keep obligations charged. Publication/retirement requires a durable journal and exact identity checks. No cleanup of arbitrary originals, export destinations, unrelated mounts or unknown files is authorized. Uninstall/database reset must respect these obligations.

## Approval scope and next work

Before approval, source-only codec/model/test design and a separately reviewed **private synthetic local** copy/read-cost prototype can be prepared without enabling either mode, exposing real files or adding grants. A real private run still needs its own reviewed bounded run plan. No such prototype has run in this proposal.

Enabling S on a mesh, retaining copied source data under a new policy, introducing F credits or exercising delegated remote delivery requires approval of these changed semantics first. No changes to host security, filesystem features, installed dependencies or OS services are requested. Unsupported capabilities report unavailable; they do not invoke privileged setup.

Concise approval choices (none enables runtime by itself):

1. **S only — recommended:** “Approve optional snapshot generations with independent charged storage, source authority retained through publication and the bounded prepared-review lifetime. Original-source changes after publication do not recall the generation. Keep F disabled and strict live-path behavior unchanged. Review and test implementation before enabling S.”
2. **S plus F semantics:** “Approve S and separately opt-in F: exact canonical chunk credits, at most eight simultaneous owned slots/eight MiB per consumer, 32 MiB per consumer authority, and at most 250 ms from each original pre-request anchor. Accept the stated bounded remote-recall/partition handoff tail and already-disclosed-data limits. Keep both disabled until all protocol, clock, lifecycle, accounting and native gates pass.”
3. **Neither yet:** “Keep both proposed modes disabled; continue the approved strict path, source/model work and separately reviewed private synthetic cost prototypes.”

Every choice retains the raw-TLS network-speed target, public consumer lifecycle, real Linux/macOS mount support and separate writable/build coherence work. This proposal does not replace any of them.

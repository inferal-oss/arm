# Connected-graph discovery and messaging — approved scheme

Status: APPROVED by the operator on October 21, 2026. Staged implementation is authorized under the review and validation gates below. Current supported product behavior remains direct-peer TLS/grants until the implementation passes those gates. This amends the original scheme: A connected to B and C should let B and C discover and message each other through A, without a direct B–C connection.

## Recommended decision

Approve a **messaging workspace** with an explicitly trusted, pinned membership-directory authority and standard end-to-end TLS over bounded ARM-only relay streams. Reuse nodes' existing self-signed public certificates and private keys; introduce no shared CA, shared password, home SSH key distribution, custom encryption or new cryptographic signature format.

Workspace membership automatically exposes a small node card and a durable host/operator inbox to other active members. Agents become individually addressable only if their local registration explicitly opts into that workspace. Membership never confers resources, run, shell, files/shares, local dashboard tokens, ordinary peer RPC, administration or arbitrary TCP forwarding.

This **does add delegated discovery and messaging trust**. Each member trusts the reviewed directory to admit exact node identities, and trusts that admitted members may address its enabled messaging endpoints. An authority or an explicitly delegated introducer can introduce new members within the reviewed policy. The old “no transitive membership/trust” sentence cannot remain unqualified. No transitive *resource/execution* grants are introduced.

## Operator approval and membership

1. A native operator creates a workspace with random stable ID, friendly name, exact directory host ID and certificate/SPKI pins, policy revision, member/relay quotas, and membership freshness limits. The local daemon is the directory initially; this role is separate from being a relay. Ordinary `arm mesh connect` stays direct-only unless its concrete review includes workspace admission.
2. Joining shows directory identity/fingerprints, current members/count, automatic visibility and host-inbox consequence, relay metadata exposure, whether this member may introduce future direct peers, and which agent registrations are exposed (default none). Default decline; no retroactive auto-enrollment of existing peers without this review. Existing A–B/A–C pairs can be included together in one reviewed migration.
3. Recommended initial automatic-join policy: an admitted **introducer** may propose a newly reviewed direct peer to the directory. Authority A can introduce its newly connected C automatically under A's reviewed policy. B may introduce D only if explicitly delegated that power. Both joining endpoints review the workspace/directory and message scope; an ordinary pair operation does not import a workspace silently. Non-introducers cannot enroll members or delegate introduction rights.
4. The directory admits an exact host ID + certificate DER hash + SPKI hash after proof of possession, with membership generation, expiry, admission provenance and monotonic directory revision. No display name, address, certificate alone, endpoint advertisement or caller field creates membership. A duplicate ID/changed key fails closed. A directory member is a new **message principal**, not an active direct `mesh.Peer`.
5. Directory reads and join intents use standard pinned TLS. Admission can be proposed through an introducer's existing authenticated channel; the directory completes a pinned proof-of-possession connection to the candidate through the closed route channel before marking active. Unadmitted candidate proof is single-purpose, short-lived, bounded to the exact introduced cert/admission ID; it cannot query members, send messages, relay onward, or access native/ordinary mesh RPC. An introducer cannot activate a candidate merely by asserting it has the key.
6. The directory identity/pin is delivered over the reviewed direct bootstrap channel. Each new member persists that exact pin before routing. Nodes use their current identity cert/key; no issuer is added. Ordinary certificate renewal changes an exact pin and requires existing reviewed renewal/rotation plus directory update. A route/advertisement cannot update a pin.
7. Directory key/certificate replacement or authority migration is an explicit operator review of old/new identities and membership policy; no automatic authority election. Loss/expiry requires out-of-band/direct verified recovery. The directory's OS-user account is trusted to admit identities and could lie at a first introduction. This is a deliberate delegation, not protection against a malicious directory. Existing member pins remain continuous; it cannot silently replace an already accepted identity.

For A–B/A–C: A is the reviewed directory/introducer; B and C join that same workspace. They receive each other's exact directory-admitted node cards and certificate pins. B opens a routed message stream through A, then performs its own pinned TLS handshake with C. C authenticates B from directory membership and sends replies over the same model. Neither needs B–C IP reachability.

## What is automatically visible / addressable

Each active member's node card contains stable host ID, friendly name, reported OS/build (bounded optional), membership generation/freshness, and node-inbox availability. Do not propagate home paths, SSH accounts/keys, IP interface inventories, process/lease reasons, contact/session IDs, arbitrary metadata, or full local status. Direct-peer details remain separately local and grant-bound.

Joining enables one **host/operator inbox** for workspace members: durable human-readable text, member-attributed, notification-only; no automatic command execution or agent dispatch. Users can immediately send B→C and reply C→B without exposing a powerful agent. Local operator can disable the inbox or mute/block a member. Visibility is not a claim that a human has read the message.

A registered agent endpoint needs local explicit workspace publication. Its directory entry contains a random workspace-scoped endpoint ID, display name, node ID, exact registration generation and bounded delivery mode; no CLI/config/cwd/session secrets. The destination retains the exact internal contact/session/registration/config mapping. Re-registration withdraws the old endpoint; no automatic retargeting to a namesake. Publication is a reviewable local change and can be withdrawn without leaving the workspace. Poll and native delivery remain separate, with native delivery's execution consequence made clear. The origin node attests its exact source registration; this does not invent per-agent cryptographic authentication beyond ARM's existing trusted OS-user boundary.

## Route discovery and transport

Separate membership from reachability. The authoritative directory gives authenticated membership snapshots, revision/expiry and exact certs. Member-to-directory links can themselves use the same closed routed transport after their directory pin is known. A bounded graph cache stores per-node route observations, not spendable grants.

Nodes report only active, mutually confirmed workspace-enabled adjacency over authenticated end-to-end calls to the directory. A routable edge needs both endpoint reports matching workspace + exact direct pairing + active generation; expired/mismatched/unilateral reports are hints only. No raw Internet addresses need to be redistributed: each relay resolves only its own already paired next-hop stable ID. Directory gives bounded path hints; each hop independently checks its immediate active pair/workspace policy and refuses an unavailable next hop. Names never select authority.

Use the already depended-on maintained `github.com/coder/websocket` for a separate versioned binary relay endpoint on existing pinned peer TLS, with normal HTTP/1.1 upgrade. Its `NetConn` adapter can carry an **inner Go TLS1.3** connection. This avoids adding arbitrary custom crypto or changing direct RPC's established HTTP/1.1 behavior. A short feasibility prototype must first prove actual cancellation, deadlines and nested TLS behavior.

Outer stream open carries only workspace, opaque route ID, exact destination stable ID, remaining path of member IDs, hop budget, class (`directory` or `message`), bounded deadline and member revisions. No URL, IP/port, Unix socket, executable, HTTP method or arbitrary handler selector. Maximum path8 nodes, no repeated node IDs, deadline30s and idle10s initially. Every hop consumes an entry; retrying another path opens a new stream, never reinterprets the current stream. Relays dial only their existing exact next-hop peer; at destination the stream attaches only to a dedicated in-process ARM messaging/directory TLS listener. There is no network socket destination chosen by the requester.

Inner TLS uses the final node's exact directory-admitted certificate, normal chain/purpose/SAN/time validation with explicit trust pools and exact DER/SPKI pins. The destination requires the exact active member client cert; derives original source from it; verifies stable source/target/workspace and membership generation; then runs a **separate closed routed API**. Do not reuse ordinary mesh dispatch/WithPeer or insert discovered members in the direct-peer store. Supported inner methods: bounded directory fetch/member card/published endpoint lookup, message send, exact outcome lookup, and reply. Everything else denies; ordinary `/v1/mesh` requests, native WebSocket upgrades, SSH/file/bulk endpoints and run/acquire/read-status are refused even if bytes look valid. Layered TLS is not authorization by itself.

A relaying node sees neighbors, source/destination routing metadata, sizes and timing, and can delay/drop streams. It cannot read or alter message bodies, directory contents or receipts inside inner TLS, or impersonate a previously pinned endpoint without its key. Relays are not trusted message authors or receipt issuers. A malicious directory remains an admission trust root as stated above; a malicious member may publish false *reported* metadata about itself. No metadata is treated as resource authority.

`websocket.NetConn` disables the library read limit: the implementation MUST restore appropriate frame bounds and use streaming bounded copies, byte quotas and connection lifetimes; no `io.ReadAll` on unbounded tunnel bytes. Define actual tested frame/read interaction in the prototype rather than assuming the adapter retains WebSocket defaults. Disable compression and TLS early data/session resumption initially. All connections use bounded handshakes and normal cert validation; never `InsecureSkipVerify` or system trust fallback.

## Freshness, revocation, partitions and merge

Proposed initial hard bounds: membership snapshot freshness60s; per-stream lifetime30s bounded by snapshot expiry and certificate expiry. Fetch/update every15s with jitter/coalescing; cached revision never moves backwards. Authenticated directory failure keeps cached display marked stale, but admits no new send/lookup/route once freshness expires. Never extend a validity window from local receipt/restart time. Recovery with an uncertain local clock or rollback fails closed until a fresh directory read; persist original authority timestamp + local high-water evidence rather than granting a new60s on restart. Exact tolerance/clock mechanics are implementation review gates.

Directory membership revocation increments generation/revision; online nodes close sessions and reject new work immediately once they observe it. Disconnected nodes may continue within the explicitly bounded unexpired membership window. **Immediate global revocation during partitions is not promised**; an offline directory eventually stops messaging even if some peers remain physically reachable. Short-lived streams cap residual exposure, and each destination can immediately block a source in its own local deny list without the directory. Direct pair revocation immediately removes that edge locally; workspace-wide membership revocation is a distinct explicit operation. If an alternate approved route exists, revoking an edge alone is not a workspace-wide ban.

No consensus, automatic leader failover, unrestricted gossip, indefinite disconnected delivery or global ordering in the first stage. A directory is an availability dependency, not a scheduling authority. A hostile relay may cause denial of service but cannot turn it into successful delivery or fresh membership.

Joining two existing workspace components requires explicit merge review: both workspace IDs/directory pins, all exposed node/agent endpoints and member count, admission/delegation/relay/freshness rules, selected continuing directory, duplicate-ID/key conflicts, and local bans. A physical pair edge between different workspaces does **not** merge them. First implementation does not federate roots: create a new reviewed workspace generation or explicitly re-enroll into one continuing authority; each node approves its migration and old-domain messages remain in their old namespace. Until done, the components stay separate. There is no silent equivalence of members or imported execution grants.

## Message identity, reply, durable results

Typed envelope (conceptual): protocol/schema, workspace+generation, exact origin host, exact origin published endpoint or host inbox, exact destination host+endpoint+registration generation, random message ID, caller idempotency key, bounded body, created/expires timestamps, optional original message reference, and source/destination membership revisions. Maximum body16KiB; complete request<=60KiB; expiry<=24h but send must occur over fresh authorized membership. No broadcast initially; route discovery is automatic, delivery remains addressed.

Origin validates its locally authenticated OS user/registered source exactly and persists the outbound immutable request/digest before dispatch. Destination derives source host from inner TLS and validates all claimed fields; rejects forged host/unknown source endpoint/replaced destination. Receipts record authoritative origin and destination node IDs plus exact registration generations. Local agent identity is node-attested, not independently cryptographically authenticated. A caller cannot use workspace metadata to impersonate another node or original sender.

Destination deduplication key is `(workspace, source_host, source_endpoint_generation, client_key)` with canonical full envelope digest and immutable destination. Same key+same request returns durable outcome read-only; different payload conflicts. Message ID collision with another origin is distinct; endpoint labels are never keys. Persist message + exact target inbox entry + native-delivery intent atomically before acknowledging accepted. Origin persists the final destination receipt. No relay acknowledges final delivery or stores plaintext. Relay acceptance means only stream admission.

Outcomes distinguish not accepted, durably accepted/available to poll, native delivery pending, acknowledged/read, rejected/superseded, expired, and **unknown**. TLS close/timeout or malformed receipt after send retains exact request/key/destination; UI offers read-only lookup, never automatically creates a new key or starts another native turn. Exact retry is allowed only via destination's committed dedup rules. Native dispatch uses existing at-most-once intent/unknown semantics; recovery never repeats a possibly completed external agent turn. Empty lookup alone after an uncertain concurrent send is not proof it cannot still commit: retain request until definitive result/expiry/fencing evidence.

Reply targets come from the original committed message's source host+endpoint+generation, not the current relay or a contact with the same name. Destination must prove the current replying endpoint was an actual original recipient; message ID possession alone is insufficient. If original sender registration disappeared, preserve reply with superseded/unavailable outcome rather than redirect it. Automatic native returned text/ack text is a durable poll reply to the original source and does not trigger another native turn. Explicit reply may request separately authorized native delivery. Avoid automatic agent-to-agent reply loops.

Reroute transport before request bytes are admitted is safe; after send begins, routing failure is unknown and performs outcome lookup first using the exact same destination+key. Rerouting must never run an arbitrary send handler again outside dedup. Local outbound queue is bounded, explicit and sender-owned; no store-and-forward plaintext at relays. A disconnected destination is unavailable; no promise that relays hold/retry messages for it. Membership revocation/published endpoint withdrawal denies new delivery and lookup per current policy; already committed target inbox/history remains local, no global erase claim.

## Limits and accounting

Initial limits to validate: workspace128 members,32 exposed agent endpoints/node,8-node routes,32 active relay streams/daemon with per-immediate-peer8 limits; final destinations additionally enforce per-authenticated-origin4 limits (relays cannot authenticate an opaque inner-TLS origin from hop headers); accept/TLS handshakes independently bounded;8 pending end-to-end deliveries/source;64KiB/frame and256KiB bounded buffers/stream;1MiB bytes/stream initially. Token-bucket byte/message/open limits and total resident buffer budget protect memory/CPU/network; reserve control slots for cancellation/revocation/lookup. Rejections are structured retry-after/overloaded outcomes; do not fabricate accepted delivery.

Directory pages and topology snapshots bounded with exact revision/cursors, no synchronous128-node fanout. Route ID replay LRU bounded/time-expiring; per-hop loop and duplicate stream checks. Malicious authorized peers can reset claimed hop fields, so hop counts alone are insufficient: lifetime/byte/rate/concurrency limits are enforced by every relay, plus no repeated active route ID and no arbitrary destination. Audit admission/membership revisions, route class/endpoints, durable message IDs/outcomes and bounded failure metadata, never bodies/keys/tunnel plaintext in operational logs. User-visible message history remains the deliberately stored inbox. Disk/retention quotas bound that storage and expired dedup tombstones prevent old-key redelivery within advertised key lifetime.

No resource claim, pool capacity or successful reclamation is inferred from member discovery. Native accounting/lease/process semantics remain unchanged. Relay overhead belongs to ARM's own bounded infrastructure, with real measurements; future network credits/claims are a separate policy feature, not invented here.

## Implementation sequence after user approval

1. Standalone pinned nested-TLS/closed WebSocket stream prototype; no production handler exposure. Confirm maintained library behavior, bounded buffers/deadlines/normal TLS checks and strict final handler isolation.
2. Typed workspace/membership records, pinned directory read/admission, clock/freshness/revocation, exact reviewed join/merge and local deny. Strict reset/schema readers must explicitly reject new records until separately reviewed; no partial allowlist widening.
3. Bounded authenticated adjacency and graph routing; no arbitrary dial, loops/unknown outcomes explicit. CLI discovery first, then matching web/TUI cards that visibly distinguish direct resource peers vs discovered messaging members.
4. Durable addressed host-inbox send/reply/lookup across the graph, followed by opt-in agent endpoints/native delivery and source-aware reply receipts. Reviewed deployment/compatibility capability negotiation; older nodes remain direct-only and cannot accidentally become relays.
5. Full independent security/source review, native/Linux/CUA/PTY acceptance and focused commit with docs describing the new trust delegation and residual limits. Separately keyed Resume/lookup remains required next portfolio work; not replaced or dropped by this proposal.

## Required real tests, not only mocked topology

- Three isolated real daemons with network rules/wrappers proving only A–B and A–C adjacency: B and C automatically discover exact IDs after reviewed workspace admission; real B→A→C host-inbox send and C→A→B reply. Assert no attempted direct B–C connection, no origin=A substitution, same message keys/receipts after restart.
- B and C's deliberately similar contact names and numeric UIDs must not merge; exact registration replacement refuses retarget. Native and poll fixtures verify reply text returns original sender, no automatic turn loop. Dedicated real Codex/Claude acceptance only on explicitly published fixture endpoints.
- Additional fourth node D makes alternate approved route for reroute. Break one edge before send, during handshake and after destination commit but before receipt; exact request yields one inbox entry/native intent and correct unknown→lookup result. Three nodes alone cannot demonstrate a nontrivial alternate path when only A–B/A–C exist; don't claim it does.
- Cyclic graph A–B–C–A and malformed repeated paths/hop exhaustion/TTL expiry/replayed route IDs; malicious immediate peer tries reset hop count, unbounded frames, slow streams, handshake floods and requests over all quota levels. Control cancellation still progresses, buffered memory remains bounded.
- Relay substitutes cert/host/SAN/expired or unadmitted cert, forged origin/contact/message ID, TLS1.2/no-client/wrong ALPN or wrong closed endpoint. MITM cannot read body or rewrite directory/receipt; capture verifies no body/contact secrets in relay logs or hop headers. Unknown workspace/member and cross-domain fake merge reject.
- **Forwarded-grant denial**: C grants A run/observe-all but none to B; B's message tunnel attempts run/acquire/status/native WebSocket/token/SSH/share/port-forward and target arbitrary IP/Unix socket. All deny at the closed end-to-end listener; C never treats A as original caller or spends A's grant. Ordinary direct grant behavior still works only on its original transport/principal.
- Fresh membership revoke closes online sessions; endpoint withdrawal denies queued delivery; node-local deny is immediate. Partition directory and test60s expiry, restart/clockrollback cannot renew cache, certificate expiry bounds sessions, no fabricated fresh data. Already accepted inbox survives without redelivery. Show honest bounded revocation delay before cache expiry.
- Join/introducer delegation/no-delegation, partial admission, directory pin rotation, workspace merge decline, duplicateID/differentkey, strict schema corruption, crash around durable outbound/destination commit/receipt and dedup tombstones. No auto authority election or unsafe pending-store clearing.
- Mixed macOS/Linux native integration, actual UI keyboard/narrow/PTY retained uncertainty/reply/source display. No private destinations or unrelated sessions in tracked fixtures.

## Protocol references / rationale

- [Go crypto/tls](https://pkg.go.dev/crypto/tls#Config) and [crypto/x509](https://pkg.go.dev/crypto/x509#Certificate.Verify): normal mutual certificate verification with explicit roots/purposes plus exact pins. Message membership is ARM authorization policy layered on TLS, not a property the certificate alone grants.
- [TLS1.3 RFC8446](https://www.rfc-editor.org/rfc/rfc8446) describes certificate authentication and replay risks of early data; no early data is proposed. No hand-rolled end-to-end encryption/signatures.
- [coder/websocket v1.8.15 NetConn](https://pkg.go.dev/github.com/coder/websocket@v1.8.15#NetConn), already in go.mod: maintained net.Conn adapter, context-bounded lifetime and deadline/close semantics; its read-limit override is an explicit implementation hazard. HTTP/2 CONNECT is an alternative maintained standard transport, but adding H2 to the existingH1 listener is unnecessary for first feasibility and would need separate review. Neither WebSocket nor CONNECT is allowed to expose arbitrary forwarding in ARM.

## Approval wording

“Allow reviewed messaging workspaces: trust the selected pinned directory and explicitly delegated introducers to admit exact node identities for automatic member discovery and addressed host-inbox/opt-in-agent messaging. Permit bounded ARM-only relaying with end-to-end pinned TLS; keep resource/execution/file/administrative grants direct and explicit. Accept directory freshness/partition availability limits and separately review joins/merges/identity changes.”

The operator approved this amendment explicitly. Implement and independently review each checkpoint; approval of the design does not establish working graph routing or waive the required real tests.

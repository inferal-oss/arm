# Routed SSH and sync over a messaging workspace — approved security extension

Status: **approved by the operator; routed SSH implementation is integrated and under native acceptance, while routed sync is unavailable** (October 25, 2026). `SPEC.md` requires SSH and sync to cross a mesh when endpoints cannot connect directly. The October 21 messaging-workspace approval covers directory and messages only. It explicitly does not grant SSH, file or execution access. The separate routed handler, private grant ledger and route-aware `arm ssh` path described here are implemented. `workspaceroute` still admits only directory/message/lookup streams. This document defines the approved trust decision and remaining acceptance boundary.

## Exact new authority

1. A source operator reviews an exact workspace ID/generation, directory DER/SPKI pin, original source and final destination stable IDs with membership generations and certificate DER/SPKI pins, destination ARM SSH host key, destination OS account/owner, route policy and resource ceilings. Changing any endpoint identity/account/key requires a new pin review. Names and graph edges are locators, never authorization.
2. Each transit node separately opts in to `ssh-relay` for this workspace and class (`ssh` and, when available, `sync`), with bounded lifetime, byte rate/total, per-neighbor streams and aggregate memory/CPU commitments. A messaging relay opt-in or workspace membership alone is insufficient. The transit node authorizes only the exact next **directly paired** mesh neighbor by its current mTLS certificate, pair ID, enrollment revision and workspace membership. It cannot select a requester-supplied IP, port, URL, Unix socket, RPC method or executable. No general TCP proxy is installed.
3. The destination separately grants **the original source certificate**, not the last relay, routed `ssh-exec` plus `lease-own` with existing TTL/resource ceilings, effective account and SSH service identity. This is an explicit new source→destination grant record keyed by workspace/generation, exact source and destination membership generations and DER/SPKI pins, destination account/owner and SSH host key. It is not inferred from directory admission, a direct grant to the relay, or graph metadata. The destination operator reviews it even if the two nodes have no direct enrollment. A future sync worker uses the same original-source execution grant plus its reviewed roots and receive policies; no relay obtains file permission.
4. The directory's approved membership delegation supplies fresh node identity/path evidence only. Directory and introducers cannot mint destination execution grants. Every hop checks its local `ssh-relay` permission and fresh membership, and the destination checks current grant, account, resource admission, service revision and original-source identity again immediately before execution. A current local deny or revocation closes the affected live stream; cached membership never extends beyond the existing 60-second workspace freshness limit, including during an established long-lived stream. A partition can delay workspace-wide revocation within that bound, as already disclosed for messaging.

## Wire and cryptographic binding

Add a **separate versioned SSH/sync route class and handler**, with a distinct HTTP path and subprotocol from both `/v1/mesh/ssh` and messaging `workspaceroute`. Reuse the tested `coder/websocket` outer carrier and `workspacegraph.Snapshot.Paths`, but not the messaging route's 30-second/1-MiB data budget or its closed method dispatcher. An open carries a random route ID, workspace/generation/revision, exact original and final IDs/generations/certificate pins, destination SSH host-key pin, immutable simple path of at most eight IDs, current hop, next direct pair/revision, class and bounded expiry. Only hop/pair/revision change during forward. Each hop rechecks current paired next-hop identity and local relay policy; route replay ID is rejected per workspace generation, and full replay tables deny rather than evict live IDs. Route hints alone are never grants.

The source and destination establish **inner mutually authenticated TLS 1.3** through the opaque carrier, using normal X.509 purpose/SAN/time checks, explicit trust pools, exact DER/SPKI pins, no resumption or early data, and a distinct SSH-relay ALPN. The first authenticated inner control record includes a digest of the immutable route fields (workspace, endpoint identities/pins, route ID, path, class and expiry); both endpoints compare it, excluding only per-hop pair/revision. The destination derives the original source from the verified inner client certificate and compares it with the route and current membership/grant; a hop header cannot assert the source. Inside this channel, a closed typed control protocol permits only destination SSH identity/admission, exact execution stream, exact key lookup/seal and the separately reviewed sync-worker exchange. It rejects ordinary `/v1/mesh` methods, arbitrary URLs, ports, generic WebSocket or SSH forwarding and any message-class request. The existing embedded SSH handshake still verifies its separately pinned SSH host key and one-use ephemeral client key. Relays see routing metadata, byte counts and timing, and can drop/delay streams; they do not decrypt command/file payload or issue final receipts.

The source durably records its original key and an immutable **endpoint authorization commitment** before any routed execution bytes: original/final identities and pins, workspace generation, destination grant revision, account/SSH host key, request digest, resources, reason, TTL, and key. A particular route ID/path is transport evidence, not part of the execution identity: a new approved route may be used for read-only same-key lookup after failure. Reroute before request bytes are sent may open a new stream; once any execution-bearing bytes may have reached the destination, loss is **unknown**. Neither relay ACK nor empty lookup proves nonexecution. Exact destination key lookup/seal follows the existing source-intent and destination receipt rules; there is no automatic new-key execution or blind sync retry.

Proposed initial per-hop bounds to measure before production: at most eight path nodes, eight active SSH/sync relays per daemon, two per immediate peer, 15-minute per-stream cap, 30-second idle cap, 64-KiB frame, 8-GiB bytes per direction, bounded buffers and a reserved revocation/control slot. A long transfer needs an explicitly reviewed continuation with the same operation key and fresh route admission, never an implicit replay; no claim is made that a 15-minute segment completes every sync. Every hop applies independent byte/lifetime/rate limits and short recurring current-authority checks. Cancellation or revocation must close both carrier sockets and join original workers; a timeout alone does not release charged source/destination sync or SSH duties. Reject oversize frames after `websocket.NetConn` resets the read limit. Limits are policy candidates, not performance acceptance.

## Integration cuts after approval

| Existing API/path | Required isolated integration |
| --- | --- |
| `internal/workspacegraph.Snapshot.Paths` | Use only fresh complete graph hints; route selection never writes discovered nodes into `mesh.Store` direct peers. |
| `internal/workspaceroute.Open`, `Handler`, `connection.go` | Reuse reviewed bounded-carrier patterns, but keep message classes and dispatcher unchanged. A separate SSH/sync route carrier must enforce its own quotas, replay and live revocation. |
| `internal/workspacetransport` | Retain closed directory/admission purpose; do not add SSH methods or assume its direct-only `Open` authorizes forwarding. |
| `internal/meshstream.Control`, `Handler` | Preserve direct SSH protocol. A routed destination adapter must derive an equivalent **original-source** execution scope from verified inner TLS and new destination grant; never call direct-peer `sshScope` using the relay's certificate. |
| `internal/server/mesh_ssh.go` and `mesh_ssh_rpc.go` | Factor destination identity/admit/execute/lookup around a typed, original-source authority snapshot and final revalidation. Register the separate relay handler only after explicit policy/schema review. |
| `internal/cli/ssh.go`, `sshservice` source history | Select direct or reviewed route; preserve source intent-before-exec, account/host-key review, one-use signer and unknown lookup. Extend pin/intent schema explicitly for routed endpoints without converting a hop pair into the execution principal. |
| Sync worker | Carry its fixed worker/control/rsync bytes in the authenticated end-to-end SSH stream; preserve independently reviewed endpoint roots, policies, resource/staging obligations and exact sync receipts. |

The implementation has a separate `/v1/mesh/ssh/route` listener, inner pinned TLS, closed identity/execute/lookup/seal requests, private reviewed relay and original-source destination grants, direct-peer-preserving CLI selection and native source-intent recovery. A read-only `ssh_identity` route class discovers the reviewed destination host key before execution; it requires the same relay and destination SSH grants and cannot execute. The `sync` class is reserved but the final handler refuses it until a fixed endpoint worker and reviewed roots/policies exist. A server-level three-daemon B→A→C test executes an SSH command without a B–C direct peer, reads an original-source receipt and rejects a new stream after transit grant revocation. Full public CLI, actual macOS/Linux, alternate-route, active-stream revocation and throughput acceptance remain to run.

## Reviewable three-node acceptance

Run three real daemons A, B, C with B↔A and A↔C only. OS network rules and dial logging must prove B cannot address C directly. Review B and C exact membership/pins, A's SSH/sync relay grant, and C's explicit routed `ssh-exec`/`lease-own` grant to **B**; also grant C's OS account/resource/SSH host key. Give C a direct execution grant to A but none to B as a negative control, then prove B is denied until its own grant exists. Use real OpenSSH through `arm ssh C` from B; verify command output, exit status, PTY and process/account/lease/history name B as source and C as destination. Capture at A must show opaque inner TLS bytes and no command/file plaintext.

Run actual `arm sync push`, `pull` and `both` B↔C through A, with content hashes, additive/full endpoint behavior, conflicts and original-key receipts. Isolate the endpoint direct link throughout. Break A↔C before open, during inner handshake and after destination commit but before receipt. Assert no duplicate execution/file effects; perform exact-key read-only lookup and explicit recovery. Revoke A's relay grant and C's grant to B separately during a live transfer; assert new opens fail, active streams close, original workers settle or remain honestly charged/unknown. Restart/revoke/expire membership and pins, exercise route replay/loop/hop/byte/stream/idle limits, and verify the existing direct SSH path still works. Run the claimed macOS and Linux native paths; record actual OS, architecture, rsync oracle and throughput evidence. The three-node test proves reachability; a fourth node is needed to test alternate-route recovery.

## Approved operator authorization

“Allow a separately reviewed `ssh-relay` transport grant on selected workspace relays, and a separately reviewed routed `ssh-exec` plus `lease-own` grant at each destination for an exact original source, pinned workspace identities, account and SSH host key. Permit only closed ARM SSH/sync streams over opaque end-to-end pinned TLS through those relays, with bounded route/quota/freshness/revocation and exact-key unknown recovery. Messaging membership or a relay's own execution grant does not grant another source shell or file authority.”

The operator approved this authorization. The implementation and server-level native three-node SSH test establish the backend path; they do not establish public `arm ssh` workflow or routed sync acceptance on both operating systems.

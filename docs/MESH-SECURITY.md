# Approved mesh security design

The operator approved this scheme on October 21, 2026. This records the security contract; `IMPLEMENTATION.md` and `VALIDATION.md` distinguish implemented commands and verified behavior from remaining scope.

The operator subsequently approved the [embedded SSH/mounted-share scheme](MESH-ACCESS-PROPOSAL.md). It authorizes staged implementation of separately granted embedded services over pinned mesh streams and capability-tested unprivileged consumer mount adapters. It excludes privileged host setup and system SSH/NFS configuration changes. These services are not implemented yet; current small-JSON direct-peer support and its restrictions below remain the actual supported surface until the new gates pass.

ARM peers authenticate using TLS 1.3 mutual authentication, persistent per-node Ed25519 certificates and exact pinned public identities. Standard X.509 purpose, SAN and expiry checks remain enabled with explicit peer trust pools; there is no system-CA fallback, shared mesh password, disabled certificate verification or transitive trust. Each host keeps its stable ID. Addresses and display names locate a host; they do not establish its identity. Private key files belong to the daemon user in private state, are never exchanged, and are excluded from ordinary reports. Renewal/re-pairing is explicit. The implemented listener uses HTTP/1.1 ALPN over TLS1.3 at a dedicated `/v1/mesh` path, with explicit protocol-version and final-host checks; it is separate from native/browser WebSocket RPC. Session tickets/resumption and redirect following are disabled.

A remote listener and peer access are disabled by default. Pairing uses SSH with verified existing host keys, a fixed bootstrap command and bounded structured stdin/stdout. It never enables agent forwarding, accepts unknown host keys automatically or interpolates peer metadata into remote shell source. The operator reviews identities/fingerprints, endpoints and exact directional grants before applying changes; noninteractive execution requires explicit consent. Short-lived pending enrollment grants no operational rights and must prove possession of the exact paired identities. Interrupted pairing is reported with its key/stage, not inferred successful. The initial SSH path is direct-only: effective ProxyJump/ProxyCommand are refused. The verified main-client account/host-key transcript is isolated from remote banners and child logs, and mutation stdin waits for that identity to match review. Host-key/DNS first-contact bypass, known-host mutation, multiplex reuse, configured commands and agent/X11/GSSAPI/tunnel/environment forwarding are disabled or rejected. Automatic `mesh connect` may start the compatible installed backends and prepare private identities and exact bound-but-not-listening sockets before review. No listener/trust is enabled before approval; decline closes reserved sockets, while ordinary backends/private identities may remain. Dry-run and missing machine consent create no ARM state. The approved endpoints must be reachable in both directions for possession proof. Configured enabled endpoints recover at the same address on restart; failures preserve configuration and local authority without silent rebind. A bounded adapter for explicitly synthetic loopback/port-zero SSH gateways accepts only unambiguous native assigned private interfaces and a verified kernel-selected local route; DNS is a locator, never authentication. `disconnect` revokes exact enrollment locally first, records unavailable opposite revocation as pending, and preserves resource obligations/other peers. Delayed old requests cannot revoke re-enrollment.

Authentication and authorization are separate. The default requested target grant is read-only aggregate host observation; reverse grants default to none. Lease changes, execution and contact/message access require their own explicit directional grants. Remote broadcasts are refused in the initial API; unrecognized operations deny by default. Read-only summaries exclude unrelated paths, lease reasons, contacts and message bodies. The mesh listener exposes a narrow API and cannot mint browser/local credentials, change trust, stop the daemon, install integrations or forward full native RPC. A peer acts only on its own authorized leases. Grants have explicit resource/TTL ceilings and are checked for each operation. Revocation prevents subsequent operations and closes existing sessions; already committed work retains its local obligations and expiry until an explicit authorized lifecycle action ends it.

**Arbitrary remote execution runs as the destination ARM user's OS account and is not sandboxed.** It can access that user's files, credentials and ARM keys/configuration. A run grant therefore conveys the practical privileges of that account; own-lease API checks do not contain arbitrary same-user code. ARM never implies stronger isolation, privilege escalation, source upload, environment forwarding or local-path reinterpretation. Stronger boundaries require a separate restricted account or a future verified sandbox.

Mutations retain authenticated origin, the actual admitting certificate fingerprint/grant revision, explicit final authority and durable exact-request retry keys. Native caller-supplied source metadata is discarded. Authentication metadata is excluded from semantic retry matching while the original admission record remains unchanged. A lost acknowledgement is an uncertain outcome, never permission to run again with a new key or on another host. Reconnect/lookup is read-only; native message delivery is never silently reinvoked. Bounds apply to connections, handshakes, calls, request/response bytes and operation duration. Revocation must not be held indefinitely by a slow delivery or client.

Host-directed peering messages select a stable host ID or unambiguous name and an explicitly authorized destination audience. The receiver records the authenticated origin rather than trusting supplied sender metadata. Contact IDs must be explicitly allowed and agent sends bind their reviewed registration. Operator-inbox access is a separate scope option; contact-read is not implicit in message permission. Contact changes cannot silently retarget a reviewed send, and read-only lookup rechecks current audience/contact scope before returning later replies. Permission to message a powerful agent is a trust decision, not a sandbox. A paired peer cannot relay operations through another host's credentials to gain transitive access. The first version uses explicit direct peers; discovery, multi-hop routing and membership propagation require a further protocol.

Each host owns its admission ledger, process identity, resource accounting, expiry and reclamation. Disconnection does not manufacture free capacity or transfer ownership. A global pool keeps one explicit authority; unavailable authority denies new commitments. Initial claims spanning multiple authorities are rejected rather than presented as atomic. The implemented remote path also refuses queued claims, all custom-pool bundles and managed storage/port/agent or usage-policy attachments; immediate native cooperative budgets and destination-local supervised commands are its initial resource surface. Automatic placement, distributed transactions, global authority replication/failover, gossip, public relays and automatic NAT/tunnel orchestration remain separate work.

Certificates last one year. `mesh renew` explicitly renews or recovers an expired local certificate using the same private key/SPKI, changes the DER pin, closes sessions and revokes local peer grants. Reviewed `join --replace-revoked` enrolls a fresh proof and explicitly supplied grants; active pins cannot be replaced implicitly. Private-key rotation and automatic endpoint reconfiguration remain future work. Expired peers remain inspectable but cannot authenticate; one expired peer does not disable healthy peers or the local backend.

Private state is verified through owned directory descriptors and no-follow regular single-link files; writes use private same-directory temporary files, fsync and rename with identity rechecks. Durable trust history records actor/time/reason/pair/pins and the reviewed identity/grant digest. Limits are 64 peers, 1,024 trust events and 1 MiB of configuration; full history refuses changes rather than deleting audit records. Transport bounds include 64 accepted sockets before TLS, 32 handlers globally and four per peer before body reads, 64 KiB requests, 4 MiB replies and deadlines. Ordinary kernel I/O is not hard preemptible, and the daemon account/root is outside the tamper-resistance boundary.

Acceptance uses isolated local and Linux hosts: actual pairing and dispatch, SSH host-key refusal, certificate/pin/SAN/expiry rejection, grant/other-owner denial, explicit run consent, revoked sessions, exact retries after lost responses, autonomous expiry while disconnected, host-addressed messaging, metadata filtering and unsupported multi-authority refusal. Private test destinations must remain outside tracked files and Git objects.
